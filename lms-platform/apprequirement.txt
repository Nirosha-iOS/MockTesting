AI Agent Ready Specification: LMS Admin + Mobile Platform
1. Objective

Build a role-based Lead Management System with:

Admin web application
React Native mobile application
Java Spring Boot backend
Shared design system and centralized theming
Strong security, audit, lifecycle, reporting, and offline capabilities

This specification is intended for AI agents generating code, architecture, database design, APIs, screens, and workflows.

2. Final Technology Decision
Backend
Java Spring Boot
Spring Security
OAuth2 / OIDC / SSO
JWT / refresh token
PostgreSQL
Redis
Object storage for files
Scheduler/jobs for SLA, reminders, inactivity, report scheduling
Optional messaging: Kafka or RabbitMQ
Optional search: Elasticsearch / OpenSearch
Admin Application
React web app preferred
Responsive desktop/tablet layout
Consumes backend REST APIs
Mobile Application
React Native
Offline local database: SQLite or Realm
Push notifications
Camera/file upload support
Sync engine
3. Product Split
Admin App Purpose

For configuration, operations, assignment, dashboards, campaigns, reports, approvals, and customer oversight.

Mobile App Purpose

For field agents to capture leads, manage assigned leads, perform follow-ups, handle meetings/calls/tasks, upload files, and work offline.

validate required fields

run DNC check
run duplicate check

save lead
initialize lifecycle stage = New
write history log
7.3 Lead Assignment Flow

assign lead to user/team
notification sent
assignment history logged
7.4 Agent Action Flow

performs call/meeting/task/note/message action
activity saved online/offline
lifecycle updated if rules match
reminder and next follow-up generated
manager dashboard updated
7.5 Aging and Inactivity Flow

7.6 Campaign Flow

7.7 Conversion Flow

referral and retention workflows enabled
7.8 Reporting Flow
transactional data stored

reports generated with row-level security
exports and scheduled delivery handled
8. Backend Architecture Specification
8.1 Architectural Style

Use a modular monolith with strong boundaries first. Split to microservices only when scale requires it.

Core principles
domain-driven module boundaries
clean architecture
SOLID principles
shared kernel only for common abstractions
no direct cross-module repository access
communication through application services/events/interfaces
DTOs for API contracts
entity encapsulation in domain layer

8.4 SOLID Rules
Single Responsibility: one service/use case per business purpose
Open/Closed: support extension via strategy/policy interfaces
Liskov Substitution: interchangeable implementations for integrations and storage
Interface Segregation: smaller focused interfaces per concern
Dependency Inversion: depend on interfaces, not concrete adapters
8.5 Cross-Cutting Standards
centralized exception handling

role and field-level authorization
request tracing/correlation IDs
validation framework
standard API response wrapper
optimistic locking where needed
soft delete where required
immutable audit tables for critical actions
